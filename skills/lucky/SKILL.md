# /lucky — 我的开发方式

人只描述愿景和目标，实现由 agent 承担。

## 偏好

1. **人只给愿景。** 实现细节靠反复挖代码、评估可行性得出，不拿来问人。真遇到瓶颈，把选择翻译成用户可见的功能差异再让人权衡，不解释内部原理。
2. **追问仅限产品层。** 愿景不清才追问，只问「要什么、给谁、什么算做成、边界在哪」；一次问完，每题带推荐答案。技术实现和代码自己权衡、自己选一个推荐解，不把方案摊开让人选，尽一切可能找最优解。
3. **统一话术。** `GLOSSARY.md` 是人和 agent 共用的词表，`DECISIONS.md` 记人做过的决策权衡，供后续 agent 参考。
4. **agent 的记账本。** `LESSONS.md` 记执行中反复出现的问题和翻车证据，`docs/code-standards.md` 记同一条被踩多次、需要逐条核对的约束。能写成测试或 lint 的，不写成文档。
5. **TDD 优先，可逆就先做。** 有便宜的本地测试路径就红 → 绿；测试路径昂贵、依赖集成环境或不清楚时，换最接近的可执行验证，不硬造测试。凡可逆的直接改，事后报结果，人事后决策；被否决就回退。只有四类动作停下来等确认：force-push 共享分支、部署、删数据、对外发消息。实现成本只决定验证投入，不决定要不要问人。
6. **不产出 spec。** 任务开头一句话写下目标和最小改动，然后开始。

## 每次任务

- 读目标项目根的 `AGENTS.md`、`GLOSSARY.md`、`DECISIONS.md`、`LESSONS.md`（有才读），一句话写下目标和最小改动。
- 把愿景和目标写成 TDD 或 e2e 测试，用它们验收。
- 术语被澄清、人拍了板，当场写进对应文件；能跑一次回答的问题自己跑。
- 做完带出：改了哪些地方、验收结果、需要人拍的取舍。翻车写 `LESSONS.md`；同一错误第 3 次，记进 `docs/code-standards.md`。

四个文件都在**目标项目**里，第一次要写时才建，不预先建空文件。前两个人和 agent 共用，后两个是 agent 自己的账。

## 请人拍板时的格式

只在功能层说话，最多三行：

```
选项 A / B：用户分别会得到什么、失去什么
推荐：X
```

技术原因留在代码和日志里。若某个问题跑一次就能裁决，别问人。

## 四个文件的格式

`GLOSSARY.md` — 只写词，不写实现细节，不当 spec 用：

```
| 词 | 一句话意思 | 不用哪个含糊说法 |
```

`DECISIONS.md` — 只记**人**从功能上做的取舍，不记 agent 的技术选型，不写步骤：

```
| 日期 | 拍了什么 | 功能上的理由 | 影响范围 |
```

`LESSONS.md` — 给 agent 自己看：

```
| 日期 | 怎么坏的（现象+复现） | 根因 | 后来靠什么守住 |
```

`docs/code-standards.md` — 同一条教训在 `LESSONS.md` 出现 ≥3 次、且测试/lint 守不住时，才写成一条评审逐条核对的清单项。

## 加规则的门槛

新偏好或新规则要进入这个入口，必须先在真实会话里出过故障。假想改进只记进 `LESSONS.md` 观察，不往这里加字。
